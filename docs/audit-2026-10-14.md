## 2. Executive summary

**The core hook logic is sound and unusually well-verified. No critical security flaws found.**

The full lifecycle (config → pool → street bets → tail rule → graduation → hook revocation →
DAMM v2) was proven end-to-end on devnet. The real issues are in the **management surface**
(a bricking footgun in `set_pool`), a few **missing hardening checks** (pool owner, mint
validation), and **repo/process debt** to close before mainnet.

## 3. Findings

### A. On-chain (decide before mainnet)

#### A1 — `set_pool` is a bricking footgun — MEDIUM-HIGH

Location: `programs/hook/src/lib.rs:74`

Once `initialize_extra_account_meta_list` has run, the extra-metas PDA is immutable
(`init`-only, never `mut` — which is correct). It bakes the pool address in statically.
If the deployer then calls `set_pool` with a new pool, the per-transfer check
`pool_ai.key() == cfg_pool` (`lib.rs:200`) fails **forever** → every transfer (buy AND sell)
reverts, funds stuck. The code comment "Re-run init_extra_metas after" is impossible:
re-init fails on the already-existing account.

Recommendation (pick one):
- **delete `set_pool`** (mainnet pool is final anyway) — recommended;
- or guard it: only allowed while the `["extra-account-metas", mint]` PDA account does not exist.

#### A2 — Pool account ownership is never checked — MEDIUM

Location: `lib.rs:199-204` (+ mock-layout fallback in `read_base_reserve`, `lib.rs:295-308`)

The hook reads `base_reserve` from the configured pool but never checks
`pool.owner == DBC program ID`. Only the deployer can set the pool (config PDA, authority-gated),
so an attacker can't swap it — but a deployer typo (or a 16-byte attacker account hitting the
mock-layout fallback that exists in the production binary) lets a fake "pool" lie about the
vault balance and thus about the tier.

Impact is bounded: worst case = token runs at S4 rules forever (≤ 50k bet/tx, ≤ 20M hold —
the most permissive street). Not an exploit beyond the design's own maxima, but the fix is 2 lines:
`require_keys_eq!(*pool_ai.owner, DBC_ID, WrongPool)`. Also consider gating the mock-layout
branch of `read_base_reserve` behind test-only builds.

#### A3 — `initialize_config` does not validate the mint — MEDIUM

Location: `lib.rs:52`

`mint` is a `CHECK:` unchecked account. Nothing verifies the mint actually carries a
Token-2022 TransferHook extension pointing at this program (and ideally
`transfer_hook::authority == POOL_AUTHORITY`). A misconfigured mint silently produces a config
that can never work. Cheap hardening: parse the mint data in the handler and require the
TransferHook extension with `program_id == us`.

#### A4 — DBC mint authorities are live and unverified — MEDIUM (verification item)

Live devnet check (both pool mints, read-only RPC, 2026-10-14):

```
pool#1 48EBUqvr…  supply 1_000_000_000e6  mintAuthority 4uQeX9Q9LgTJuNiqFhnfrB9e4tAbBeYnEf9MLSgmVQo
pool#2 JBaZd2G…   supply 1_000_000_000e6  freezeAuthority 4uQeVj5tqViQh7yWWGStvkEG1Zmhx6uasJtWCJziofM
```

Neither authority is empty and neither is the deployer key (`AHe1Y4…`), and both pools share
the same authorities (consistent with a per-config PDA). They are almost certainly
DBC-program PDAs → only DBC can sign them, and DBC does not issue `freeze`. **Unverified.**
Action: confirm with Meteora / DBC source that these PDAs cannot be abused to mint or freeze
user ATAs, for both devnet and the future mainnet mint.

#### A5 — Token-account mint field not cross-checked — LOW

Location: `parse_token_account`, `lib.rs:285`

Reads owner + amount only, not the account's mint field `[0..32]`. Harmless today (Token-2022
validates mint consistency before the hook CPI; the fallback path is read-only), but a 2-line
check makes the proof self-contained.

#### A6 — `fallback` does not check `authority.is_signer` — LOW (safe by construction)

Real CPI path: Token-2022 validated the signature before calling the hook.
Direct-call path: the fallback only reads state, moves no funds. Safe — but add a comment
so a future reader doesn't "fix" the wrong layer.

#### A7 — Upgrade authority = single keypair — OPEN DECISION

`target/deploy/hook-keypair.json` (gitignored, on disk). Devnet history proves post-pool
upgrades are dangerous (discriminator-trap incident, see changelog). Mainnet plan:
finalize logic now → deploy → move authority to multisig or renounce. Undecided (docs §7.3).

### B. Design / process

- **B1 — Hook is revoked at graduation** (DBC `revoke_transfer_hook`, proven on devnet):
  no bets, holds, or P2P ban after the curve completes. Inherent to DBC and accepted
  (AGENTS.md). Only defense = 23 256 SOL migration threshold + tail rule. State this
  explicitly in the final spec so nobody "forgets" it later.
- **B2 — Aggregator compatibility (Jupiter/fomo) never verified on-chain.** Devnet E2E used
  only the Meteora SDK path. Any DEX must fetch the mint's extra-metas PDA and pass
  config+pool into the swap; this is untested mainnet-launch risk.
- **B3 — fomo `ExactIn` mid-curve dust reverts** (`== bet` strictness). Known, accepted
  (docs §7.1). UX issue only.
- **B4 — `migration_lock` is set once at init, immutable** (legacy accounts → strict forever).
  By design. Consequence: the off-chain `vault_0 − buyable_0` computation must be bit-exact
  at pool creation (it was: verified byte-for-byte on pool #2). Keep this verification step
  in the mainnet runbook.

## 4. What's genuinely solid (verified)

- **Tier/tail/hold math**: pre/post reconstruction correct (Token-2022 debits/credits before
  the hook CPI), all `checked_*` arithmetic, tail dust tolerance (459 raw units measured live).
  22/22 unit tests pass, including legacy 105-byte config fallback and strict-mode
  direct-call rejection.
- **Any-DEX safety**: extra-metas are mint-derived (`["config", mint]`,
  `["extra-account-metas", mint]`) + static pool only. `Seed::AccountKey { index: 1 }` = mint
  verified against `spl-transfer-hook-interface 0.9.0` source — CPI list is
  `[source, mint, destination, authority, extra_metas_validation, …resolved]`.
- **Extra-metas PDA is init-once** (not re-initializable); the handler re-derives both PDAs
  and re-binds config → mint → pool on every transfer.
- **Concurrency**: multiple swaps in one tx re-evaluate on updated state (accounts locked);
  tail race-safe (a second final buy sees `buyable = 0` → revert). Sells stay exact, so the
  vault can never be drained below `lock + dust`.
- **Devnet proof (changelog + §8)**: exact 50k buy at $0.21 (matched curve model),
  30k → `InvalidBetSize` on-chain, P2P → `P2PBlocked`, sell pass, fee claim ~0.20%,
  tiny-pool graduation → hook revoked same swap → DAMM v2 `isMigrated = 1`.
- **Process**: `agent-changes.json` captures the full incident history (tail trap making
  graduation mathematically impossible, discriminator trap bricking legacy pools,
  post-transfer semantics fix). Excellent discipline.
